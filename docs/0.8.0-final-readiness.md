## OAuth evidence and remaining blocker

Source-aware disposable WordPress 7.1/PHP 8.5/SQLite browser probes passed discovery, repeated public DCR, web-profile login return to consent, client persistence across activation cycling, owned/REST authorization redirects, invalid nonce/session and malformed-PKCE rejection, approval/code exchange, and authenticated MCP initialize/list/read.

Rejected token responses lack the cache protection planned in #531. On 19 September the owner explicitly deferred that header-only hardening to 0.8.1 and authorized reconciling the 0.8.0 gate. No token code changed. A tested version-limited exception reports missing headers only on credential-free OAuth error responses in exactly 0.8.0. It does not relax successful-token cache protection or any response status, PKCE, consent, replay, rotation or authorization check, and fails closed for 0.8.1. The full browser suite now passes with three explicit deferrals, including successful refreshed-token MCP use, replay rejection, denial and wrong-PKCE rejection.

Earlier fixture failures are retained separately: activation overwrote the deliberately competing test rewrite until the fixture restored it; browser callback interception did not receive the redirect, so the harness now uses an actual loopback callback server. Neither correction changed the product OAuth flow. No tokens, authorization URLs, cookies, or credentials are included in diagnostic output.
