# MCP Apps delivery model for 0.9.0

Status: owner-approved for the 0.9.0 pilot on September 25, 2026. The owner chose **self-hosted, per-site, opt-in only**. This decision does not approve a hosted service, public directory submission, analytics, uploads, or a change to Aculect's privacy policy.

## Decision

Use self-hosted, per-site MCP Apps resources for the 0.9.0 pilot. The plugin package would contain versioned, immutable widget assets; each connected WordPress site would serve them through its existing authenticated MCP endpoint. Keep the pilot disabled by default until exact-package host and fallback proof is accepted. Do not introduce an Aculect-hosted control plane, content proxy, central site registry, uploads, remote UI assets, or telemetry as part of this choice.

The owner accepted this bounded model in the 0.9.0 planning conversation. The long-term delivery model is not settled by the pilot. A hosted variant needs a separate decision. This is not approval for release or public promotion.

## Architecture and trust boundaries

```text
Self-hosted pilot
Assistant host / sandboxed view
       | OAuth-protected MCP calls and UI resource reads
       v
Each customer's HTTPS WordPress site / Aculect plugin
       | existing WordPress permissions and site data
       v
WordPress database and runtime

Hosted alternative (not approved)
Assistant host -> Aculect service -> linked WordPress site -> database
                     | tenant identity, secrets, logs, operations
                     v
              Aculect infrastructure
```

The assistant host is already a separate trust boundary for any authorized MCP result. The pilot adds a packaged HTML view delivered by the site; it does not add an Aculect server between host and site. WordPress and OAuth remain the authority for all data and actions. The view's messages and capability advertisement never grant permission.

## Options and boundaries

| | Per-site, self-hosted | Aculect-hosted service |
| --- | --- | --- |
| Request path | Host ↔ site's MCP/OAuth endpoint ↔ WordPress data | Host ↔ Aculect service ↔ linked WordPress site, if proxying |
| Data handled by Aculect infrastructure | No new processing boundary for tool results or site content | Potentially site identifiers, credentials, tool input/output, content, media, logs, and widget state |
| Primary risk | Variable WordPress hosting, TLS, CDN/WAF, versions, and uptime | Central outage or compromise, cross-tenant isolation, token custody, site-linking, retention, and incident response |
| Operating cost | Compatibility tests and support; site owner supplies hosting | Service hosting, observability, security operations, support, and possibly storage/egress |
| Distribution | Fits existing per-site connection model; host compatibility needs proof | Stable central endpoint may ease some distribution paths, but public submission and eligibility are unproven |

Neither option keeps data solely on the WordPress site: an authorized MCP tool response is delivered to the connected assistant host under the existing connection. An embedded view must not bypass server-side OAuth scopes or WordPress capability checks. UI capability declarations and iframe messages are presentation signals, never authorization.

## Data inventory and privacy impact

| Data | Self-hosted pilot | Hosted alternative if later approved |
| --- | --- | --- |
| Site identity and content | The existing MCP response goes from the site to the authorized host. The first view shows only site name, home URL, WordPress version, theme name, locale, and timezone. No Aculect-operated collection. | A proxy could see site identifiers, content and tool input/output; purposes, minimization and deletion would need approval. |
| Media/uploads | No new upload or storage path. | Proxy/storage, scanning, retention, and egress would be new obligations. |
| OAuth credentials/tokens | Existing per-site OAuth validation; no token is sent to the view or Aculect. A hashed token ID is used locally for legacy capability negotiation. | Linking and token custody would require tenant isolation, rotation, revocation, and incident handling. |
| Analytics/logs | No new analytics or external calls from the view. Existing WordPress/server logs remain under the site operator's control. | Central telemetry could collect identifiers and payload metadata and would need an explicit retention policy. |
| Widget state | Ephemeral in the host-rendered view; no browser storage or server persistence. | Persisted state would require purpose, access control, export/deletion, and migration design. |

The pilot does not change Aculect's privacy policy or data-retention promise. Its principal incremental risk is that the host renders site-derived text in an iframe. Use text-only DOM assignment, a restrictive resource CSP, no remote assets, and no client-side authority; test malformed and cross-session inputs. Site owners still need to understand the connected assistant host's own data handling.

## Threat and operational comparison

| Concern | Self-hosted pilot mitigation or residual risk | Hosted alternative obligation |
| --- | --- | --- |
| Cross-site/user data | OAuth and WordPress capability checks at each site's endpoint; legacy UI negotiation keyed to a token, not a shared client ID. Review same-token parallel sessions and avoid leaking UI state. | Tenant/site/user authorization at every hop and isolated credential storage. |
| Untrusted content and messages | Static packaged view, `textContent`, no external script, allowlisted `ui://` URI, bounded message handler and CSP; verify in a sandboxed host. | Same UI work plus proxy-origin and central service attack surface. |
| Availability/caching | Per-site TLS, CDN and WAF behavior vary. Test cold upgrade, immutable asset URI, rollback, and stale connector metadata. | Central SLO, on-call, abuse response, backups, and migration if service exits. |
| Compromise | Scoped per-site blast radius and normal plugin-update recovery, although a compromised site can still send bad data to its own host connection. | Central compromise can span sites; requires formal incident response and revocation. |

The pilot's incremental cash cost is limited to development, compatibility testing, support and the site owner's existing hosting; its substantial cost is maintainer time across variable WordPress, PHP, CDN, WAF and host combinations. A hosted option cannot be responsibly priced without projected connected sites, request/media volumes, regions, uptime target, support hours and staffing. At minimum it would need an accountable operator for deployments, monitoring, security incidents and on-call coverage, plus budget for hosting, storage/egress and support. This unknown cost is a reason not to introduce it speculatively.

## Proposed 0.9.0 boundaries

- Preserve current MCP tool names, schemas, scopes, OAuth flow, permission checks, and text/structured fallbacks. Attach only the experimental, capability-negotiated `ui://` resource to `site.get_info` first.
- Package the view with the plugin. Allowlist resource URIs, use a restrictive CSP, no external network dependencies, no arbitrary HTML insertion, no browser storage or analytics, and no Aculect-operated relay.
- Keep UI assets versioned. If later work needs a breaking view change, publish a new URI and keep or explicitly handle the old one.
- Prove the exact ZIP in the reference host, a real compatible host when available, a non-UI client, subdirectory WordPress, and representative cache/CDN/WAF configurations before claiming support. Template MCP server URL or public-directory eligibility is not assumed.
- A host that cannot render the view still receives the original useful text/structured result. Disabling the opt-in should remove UI metadata without migrating accounts or content.

## Hosted option, if revisited later

Start with a separate proposal, cost estimate, data-flow inventory, threat model, privacy impact, and migration plan. A hosted static-asset tier would be less invasive than proxying tool calls but still adds an external domain, availability dependency, CSP allowances, and asset-version ownership. A full service adds tenant/site/user identity mapping, site-bound credential custody, revocation and unlinking, cross-tenant authorization, abuse controls, support and on-call duties, and explicit purposes and retention for every stored identifier, log, upload, and tool payload. Pricing, licensing, public positioning, analytics, retention, and subprocessors are outside this ADR's authority.

Migration should be opt-in and reversible: retain per-site tool authorization and stable `ui://` contracts, consider immutable hosted assets first, and require separately approved consent/security/privacy review before any proxy or media processing. Never switch an existing site's MCP endpoint or transmit its tool results through Aculect infrastructure silently.

## Evidence and unknowns

The [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview) describes host-rendered, sandboxed UI resources and the host bridge. [OpenAI plugin submission guidance](https://developers.openai.com/plugins/deploy/submission) covers a public HTTPS endpoint for submitted remote plugins; it does not establish that per-site endpoints are eligible for a public directory. The [WordPress plugin privacy guidance](https://developer.wordpress.org/plugins/privacy/) and [detailed plugin guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/) inform data minimization and service disclosures. No credible cost estimate is possible yet without expected sites, requests, media volume, regions, availability targets, and staffing. Host-specific compatibility and public-submission eligibility remain to be verified.
