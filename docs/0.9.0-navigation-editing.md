# Navigation editing in 0.9.0

Navigation tools work with the site's stored WordPress navigation sources. A theme
name or the block-theme flag alone does not grant editing support or permission.
Use `navigation_get_context`, `navigation_list_menus`, `navigation_list_locations`
and `navigation_list_items` first. `available_surfaces` reports classic menus and
database navigation independently; an inventory is not proof that a menu is
currently rendered on a public page.

| Source | Read and edit | Supported changes |
| --- | --- | --- |
| Classic registered menus, including classic locations on hybrid/block themes | `navigation_read_item` → `navigation_update_item` | Existing item label, custom-link URL, parent, order, target, rel |
| Registered classic location | `navigation_read_location_context` → `navigation_assign_location` | Explicitly assign an existing menu or unassign it; preserve other locations |
| Existing `wp_navigation` record on any theme | `navigation_read_block_item` → `navigation_update_block_item` | Existing native navigation link/submenu label, custom-link URL, target, rel, parent and order |
| Whole database editor record | Existing `site_editor_read_record`, `site_editor_update_record`, `site_editor_restore_record` | Existing bounded native block-content and recovery workflow |

## Block item workflow

1. List items with `navigation_id`. Select a `core/navigation-link` or
   `core/navigation-submenu` and copy its `block_path` (for example, `0.1`).
2. Read that exact item with `navigation_id` and `block_path`. Retain the returned
   `expected_state`, which binds the entire navigation record and active theme.
3. Preview `navigation_update_block_item` with the same target, state, `changes`
   and `dry_run: true`. Review the item-level before/after differences and the
   warning that published navigation changes affect every reference immediately.
4. After explicit confirmation, submit the same changes and the confirmation
   token. A completed result includes the updated item, `new_block_path` and a
   native `recovery_revision_id` when content changed. A preview has not saved.
5. Read again before another edit. Replaying a completed confirmed request uses
   the existing execution claim and does not apply the edit twice.

`changes` is a closed object. `label` is plain text up to 255 bytes; `url` is up to
2,048 bytes and applies only to custom links. HTTP(S), root-relative and fragment
URLs are supported. `target` is empty, `_self` or `_blank`; `rel` contains bounded
relationship tokens. `parent_path` selects an existing submenu in the **pre-edit**
record, or `""` for the root. `order` is the final 1-based position among **all
parsed sibling blocks**, including non-link blocks and freeform whitespace where
present. Omit it to keep the current position, or append when changing parent.
Paths use zero-based parsed indices; they are not flattened discovery order.

The tool derives the serialized content itself. It does not accept HTML, PHP,
arbitrary attributes, filesystem paths or a replacement navigation document.
Supported unrelated blocks, link attributes, submenu children, record identity,
publication state and theme assignments are retained. Native serialization can
normalize block comment formatting; preservation is verified as parsed structure,
not byte-for-byte formatting of every block comment. A no-op retains original
content bytes and creates no recovery revision.

## Authorization and limits

- Existing OAuth scopes apply: `content:read` for reads, `content:draft` for
  writes, plus role/tool policy and native `edit_theme_options`, `read_post` and
  `edit_post` for the selected record. Trusted write connections still require
  explicit confirmation. No OAuth or authorization policy is widened.
- Block writes require an unlocked editor and native revisions retaining at
  least two versions. The existing editor writer rechecks freshness before save,
  verifies the saved result and recovery copy, and reports terminal uncertainty
  without automatically retrying a partial write. Checks are optimistic; they
  are not a transaction against simultaneous native-editor or plugin-hook writes.
- Maximum block record size is 100,000 bytes, with at most 500 parsed blocks and
  20 path levels. Classic menu edits retain their existing 500-item bound.
- WordPress can store the first classic item with raw order zero. It can be read,
  but an edit must include an explicit positive `order` in its preview: the native
  menu writer treats zero as automatic placement. The tool never silently chooses
  that item's position. Existing positive orders remain unchanged unless requested.
- Dynamic page lists, theme-generated links, unknown/custom blocks, inline
  navigation inside templates, and referenced navigation wrappers are not edited
  through the item tool. Unsupported content is rejected without stripping or
  converting it. Use the native editor to review these cases.
- Menus and items are not created. Block-template reference assignment and theme
  file editing are not supported. Existing guarded deletion/recovery tools keep
  their own restrictions.
- The feature is independent of MCP Apps. Text/structured tool results and the
  existing confirmation flow work without a visual App.

## Verification

The native navigation contracts run in the hosted WordPress compatibility matrix.
They exercise core parsing/serialization and synthetic navigation through the
execution gateway, with classic and database-backed sources present together.
This proves feature combinations, not every third-party theme or public rendering.
Local OAuth, rendered browser and real-host testing remain separate proof scopes.
