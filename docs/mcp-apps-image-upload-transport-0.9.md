# MCP Apps image-upload transport decision for 0.9.0

Status: the direct, authenticated WordPress Media Library handoff is the chosen fallback. A versioned widget resource opens a plugin-owned WordPress admin upload page; that page uploads through WordPress's Media API and shows the attachment ID to the human. This is locally tested but has not been installed and proved on a WordPress site or host. In-widget upload and automatic attachment continuation are not implemented. No Aculect-hosted relay is permitted.

The [MCP Apps specification](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) supports host-mediated tool calls and UI resources, but does not define a portable browser-file upload transport. A file input in a sandboxed widget does not by itself deliver bytes to the WordPress MCP server. ChatGPT offers [optional, host-specific file helpers](https://developers.openai.com/plugins/reference), but `uploadFile` first places the file in ChatGPT's file service; downloading it to the site is not direct upload and adds retention and remote-URL-fetching concerns.

Direct widget `fetch` to the site's Media REST API is not the fallback: [WordPress cookie authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/) requires a `wp_rest` nonce and appropriate capability, and a cross-origin widget cannot safely assume access to either cookies or a WordPress nonce. Do not expose them in widget HTML, host messages, tool results, or URL parameters.

If host payload limits and the actual connection path permit an opt-in portable upload later, use an app-only MCP `tools/call` carrying a bounded image payload directly to this site's plugin, not to an Aculect service. A server-side short-lived one-use grant must bind site, actor, OAuth token/client, operation session, MIME set, size and expiry; the grant is insufficient without fresh OAuth, `upload_files`, target-ownership and policy checks. Validate bytes/signature, extension, dimensions and WordPress upload policy before creating an attachment through core APIs. Test expiry, replay/concurrency, user/site/session mismatch, invalid image and partial cleanup. The host necessarily proxies the JSON bytes; do not call this a private browser-to-WordPress transfer or promise streaming progress.

Issue [#373](https://github.com/mehul0810/aculect-ai-companion/issues/373) remains open for installed-site upload, attachment continuation, widget states, and host proof. The admin page, not the widget, reports the attachment ID after WordPress confirms success. The widget must say that the user completes upload in WordPress and returns; it must not claim an attachment was created inside the widget. The assistant must treat an attachment ID supplied afterward as untrusted and recheck ownership and current capabilities before any follow-up action.
